## 目录与命名

总架构存于 `00-architecture`；八个能力目录按截图顺序编号为 `01`–`08`。模块初始文档统一为 `design.v0.1.md`。后续可按需要新增 `api.v0.1.md`、`data-model.v0.1.md`、`adr-001-<topic>.v0.1.md` 等，不提前创建空目录。

设计文件采用 `<稳定文档名>.v<主版本>.<次版本>.md`，正文版本必须与文件名一致。例：`design.v0.1.md` → `design.v0.2.md`。主、次版本按整数比较，v0.10 晚于 v0.9。

各文档独立编号。模块 v0.1 表示首次拆分，不表示总蓝图回退到 v0.1；总蓝图的现有内容版本为 v0.2，未来内容更新应新增 v0.3 或更高版本。

## 不覆盖规则

1. 先读取当前目录索引和目标模块版本，再确定本次要修改哪些文档。
2. 为每个需要更新的文档分配未使用的新版本路径，复制旧版到新文件后编辑。
3. 在新文件填写上一版本链接、修改原因、变更摘要和受影响的上下游模块；正文交付完整设计，不只写零散差异。
4. 更新模块后新增目录索引版本，固定本次组合采用的各模块版本；未发生内容变化的模块沿用原文件。
5. 检查历史文件内容未改变、文件名和正文版本一致、相对链接存在、变更关系完整。

包括错别字修正、评审结论、批准状态变化、规范修订在内，每次已交付文档的更新都通过新文件记录。废弃版本不删除，旧版上的状态不回写；替代关系和纠错说明由新版本表达。

同一次尚未交付的新稿可以完成编写和校验；一旦交付、进入评审、被引用或提交，该版本即冻结。审批、评审记录若单独保存，也使用带版本号的文件。

## 版本增量

| 变化 | 版本规则 | 示例 |
|---|---|---|
| 首次拆分模块 | 从 v0.1 开始 | `run-service/design.v0.1.md`（路径示意） |
| 增补、澄清、纠错、评审后修改 | 次版本加一 | v0.1 → v0.2 |
| 职责、API 或跨模块契约不兼容 | 主版本加一，次版本归零 | v0.4 → v1.0 |
| 仅模块组合变化 | 新增目录索引版本 | catalog.v0.1 → catalog.v0.2 |

版本号不等于批准状态。草稿、待评审和批准是独立属性；本次模块文档均是拆分初稿，继承总蓝图的 P0 未通过状态。

## 必填元数据

每份设计包含文档 ID、版本、日期、状态、上一版本、依据、变更摘要。来源和模块依赖链接到明确版本，不用“最新版”代替。内部交叉链接使用相对路径，避免绑定本机目录。
